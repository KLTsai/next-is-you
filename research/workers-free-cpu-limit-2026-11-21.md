# Workers Free plan 10 ms CPU limit and the Python tick

Research completed 2026-11-21. Scope: how Cloudflare counts and enforces the Workers Free plan's 10 ms CPU per invocation, whether it applies the same way to Cron Trigger and Durable Object invocations and to Python Workers, which techniques reduce CPU for this project's per-minute Python tick, and how each fits the code on branch `feat/162-detail-parser-cpu`. Primary sources only: developers.cloudflare.com documentation (pages read 2026-11-21 through their `index.md` form), the Cloudflare blog only where it is the first-party source for the Python snapshot mechanism, and the source of [cloudflare/workerd](https://github.com/cloudflare/workerd) at commit `f136fb7b` (main on 2026-11-21) plus the `workers-runtime-sdk` 1.9.6 copy vendored in `python_modules/`. Each claim is labelled **Source** (what the source says) or **Inference** (my reasoning). **Unconfirmed** marks anything no source settles. Nothing was deployed and no Cloudflare API was called. The project stays on the Free plan; no paid option is considered. This is supporting evidence for [#162](https://github.com/KLTsai/next-is-you/issues/162) and [#136](https://github.com/KLTsai/next-is-you/issues/136), not implementation authority; adopt anything from it through a GitHub issue first.

Measured facts used (from [`docs/HTTPS-SERVICE.md`](../docs/HTTPS-SERVICE.md), "Detail-page reader CPU check (Issue #162, 2026-11-21)"): on Staging, held tick only, the Worker `scheduled` invocation used 5 to 27 ms CPU (median 14, 11 of 15 above 10 ms) and the Durable Object `scheduled_tick` invocation used 3 to 8 ms; every invocation ended `ok`. In local workerd the detail-page parse added about 3 ms (11 KB page) to 6 ms (53 KB page).

## Summary of answers

1. **I/O wait does not count; enforcement is "terminate when consistently over", not per-invocation exact.** CPU time "measures how long the CPU spends executing your Worker code" and waiting on `fetch()`, KV or database queries "does not count". Each isolate "has some built-in flexibility to allow for cases where your Worker infrequently runs over the configured limit. If your Worker starts hitting the limit consistently, its execution will be terminated". The outcome is `exceededCpu`, and HTTP clients get Error 1102. No source quantifies the flexibility (no window, no average, no count). That explains why 11 of 15 ticks above 10 ms still ended `ok`, but it does not promise they will keep doing so.
2. **Cron Triggers: 10 ms on Free, stated explicitly.** **Durable Objects: each RPC call and each alarm is its own invocation with its own CPU accounting, but the Free plan's DO CPU budget is stated inconsistently** (the DO limits table says 30 seconds by default without a plan split; the DO FAQ says DOs "have the same per invocation CPU limits as any Workers do"). Plan for 10 ms per DO invocation until proven otherwise.
3. **Python startup: top-level imports run at deploy time, not per request.** Cloudflare executes the entrypoint module "and everything it imports at top level" at deploy and snapshots the WebAssembly memory; a cold isolate restores the snapshot. So FastAPI's import is not re-run per Cron tick. Whether snapshot restore or isolate startup is charged to the first invocation's CPU time is **unconfirmed**; the docs give startup its own 1 second limit. Python Workers also get a runtime warning signal near the CPU limit, which raises `CpuLimitExceeded` (a `BaseException`) inside Python code.
4. **The Worker `scheduled` handler runs two lines of user code** (`src/worker.py` lines 1207-1209). Its 5 to 27 ms is almost entirely Python runtime overhead per invocation, very likely including cold isolate starts, because Cron Workers "run on underutilized machines". **Inference**, not measured.
5. **Top techniques, in expected value order:**
   - (a) **Take the Cron entry off the Python Worker.** Either a small JavaScript Worker owns the Cron Trigger and calls the Python DO through a cross-script DO binding, or the DO schedules itself with alarms. Either removes the 5 to 27 ms Python Worker invocation. The alarm route also removes idle ticks.
   - (b) **Split the DO tick into separate invocations.** Lifecycle cleanup runs in one RPC or alarm; each hospital read and its evaluation runs in another. Each invocation then carries 3 to 8 ms plus one parse, not everything.
   - (c) **Cut the DO's own CPU.** The ledger digest re-reads and hashes every outbound event at least twice per tick. The parser can work on a pre-sliced fragment or use a regex extractor instead of `html.parser` over the whole page.

   A JavaScript HTMLRewriter Worker for parsing would also take the parse out of Python, at the cost of a second language and Worker.

## 1. How CPU time is counted and enforced

### 1.1 What counts

**Source** ([Workers limits, CPU time](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)): "CPU time measures how long the CPU spends executing your Worker code. Waiting on network requests (such as `fetch()` calls, KV reads, or database queries) does **not** count toward CPU time." The Free column lists "CPU time per HTTP request | 10 ms" and "CPU time per Cron Trigger | 10 ms". "The average Worker uses approximately 2.2 ms per request. Heavier workloads that handle authentication, server-side rendering, or parse large payloads typically use 10-20 ms."

**Source** ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)): Free is "10 milliseconds of CPU time per invocation".

**Source** ([Durable Objects limits FAQ](https://developers.cloudflare.com/durable-objects/platform/limits/#can-i-increase-durable-objects-cpu-limit)): "CPU time is active processing time: not time spent waiting on network requests, storage calls, or other general I/O, which don't count towards your CPU time or Durable Objects compute consumption."

**Source** ([Workers Trace Events, CPUTimeMs](https://developers.cloudflare.com/logs/logpush/logpush-job/datasets/account/workers_trace_events/)): "The amount of CPU time used by the Worker script, in milliseconds." CPU and wall time also appear in the Workers Logs invocation log ([limits, Monitoring CPU usage](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)).

**Inference.** For this tick, the awaits on D1, on DO storage, on the DO RPC and on the hospital `fetch()` are not CPU time. The Python work between them is: building SQL, converting each D1 result from JavaScript to Python, `json.dumps`, hashing, parsing and evaluation. So is the Pyodide FFI work at each boundary.

### 1.2 Startup, snapshot restore and the first request

**Source** ([Workers limits, Worker startup time](https://developers.cloudflare.com/workers/platform/limits/#worker-startup-time)): "A Worker must parse and execute its global scope (top-level code outside of handlers) within 1 second." Exceeding it fails deployment with `Script startup exceeded CPU time limit` (error code `10021`). The limit is 1 second on both plans.

**Source** ([How Python Workers work](https://developers.cloudflare.com/workers/languages/python/how-python-workers-work/)): at deploy, "Cloudflare executes the Worker entrypoint module and everything it imports at top level and then take a snapshot of the Worker's WebAssembly linear memory. Effectively, we perform the expensive initialization work at deploy time, rather than at runtime." Then: "When a request comes in to your Worker, we load this snapshot and use it to bootstrap your Worker in an isolate, avoiding expensive initialization time."

**Source** ([Python Workers redux, 2025-12-08](https://blog.cloudflare.com/python-workers-advancements/)): on a cold start "we restore the memory snapshot and the Worker is ready to handle requests, with no need to execute any Python code in preparation". A Worker importing fastapi, httpx and pydantic cold-starts in about 1 second with snapshots and about 10 seconds without. "A cold start is far more expensive in Python than in JavaScript."

**Source** (workerd source). [`python-entrypoint.js` line 40](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/python-entrypoint.js#L40) runs `await initPython()` at module top level, so Pyodide load or snapshot restore and the main-module import happen during isolate startup, not inside a handler. [`initPython`](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/python-entrypoint-helper.ts#L618) ends with `maybeCollectDedicatedSnapshot` (line 670). On the first request in an isolate, [`entropyBeforeRequest`](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/internal/topLevelEntropy/lib.ts#L189) runs Python once to reseed random number generators and remove import patches.

**Unconfirmed.** No source says whether isolate startup or snapshot restore is charged to the first invocation's `cpuTime` or counted against its 10 ms. The docs treat startup as a separate 1 second limit. Neither the docs nor the blog answer it. CPU limit enforcement lives in Cloudflare's production runtime, not in open-source workerd.

**Inference.** Even if a restore is not charged, the first request in a fresh isolate does extra Python work: the entropy reseed, and the first use of lazily built objects such as the introspection module ([`getIntrospectionMod`](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/python-entrypoint-helper.ts#L553)).

### 1.3 Enforcement: grace, outcome, timing

**Source** ([Workers limits, CPU time](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)): "Each isolate has some built-in flexibility to allow for cases where your Worker infrequently runs over the configured limit. If your Worker starts hitting the limit consistently, its execution will be terminated according to the limit configured." On exceeding: "Cloudflare returns Error 1102 to the client with the message `Worker exceeded resource limits`. In the dashboard, this appears as `Exceeded CPU Time Limits` under Metrics > Errors > Invocation Statuses. In analytics and Logpush, the invocation outcome is `exceededCpu`."

**Source** ([Tail handler, outcome](https://developers.cloudflare.com/workers/runtime-apis/handlers/tail/)): `exceededCpu` means "The Worker invocation exceeded either its CPU limits". The outcome can differ from the response. For example, "a script sends a successful `200` response but an asynchronous task registered via `waitUntil()` later exceeds CPU or memory limits."

**Source** (workerd source, Python-specific). The runtime has a "CPU time is nearly exhausted" signal for WebAssembly instances ([`tracked-wasm-instance.h` lines 24-33](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/workerd/io/tracked-wasm-instance.h#L24)). Pyodide registers for it with `setCpuLimitNearlyExceededCallback` ([`python.ts` lines 203-221](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/internal/python.ts#L203)). Python handles the signal by raising `CpuLimitExceeded("Python Worker exceeded CPU time limit")`, a subclass of `BaseException` ([`introspection.py` lines 96-105](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/internal/introspection.py#L96)). If the isolate is killed for exceeding its limit, the runtime writes a "terminated" flag ([same header, line 31](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/workerd/io/tracked-wasm-instance.h#L31)).

**Unconfirmed.** No public source gives:
- how large the flexibility is;
- whether it is time-windowed, averaged or counted per isolate;
- whether startup counts toward it;
- what "nearly exhausted" means in milliseconds.

The Staging result (11 of 15 ticks above 10 ms, all `ok`) is consistent with "infrequently" being generous, with startup being reported but not enforced, or with both. It does not tell them apart.

**Inference, project consequences.**
- On a Free-plan cut, the tick can stop mid-way. Python would raise `CpuLimitExceeded`, which `except Exception` does not catch, so an awaited D1 write sequence could be left half done.
- The send gate's ledger and recovery hold exist for an interrupted send, but a lifecycle step cut mid-way should also be idempotent on the next tick.
- Cron has no client, so no 1102 page appears. The only signal is the `exceededCpu` outcome in logs or tail.

### 1.4 Cron Triggers, Durable Object RPC and alarms

**Source** ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)): Cron Trigger CPU on Free is 10 ms. The 15 minute figure is only the wall-time limit ([Wall time limits by invocation type](https://developers.cloudflare.com/workers/platform/limits/#wall-time-limits-by-invocation-type)). [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/): "Workers scheduled by Cron Triggers will run on underutilized machines". Free accounts get 5 Cron Triggers ([account plan limits](https://developers.cloudflare.com/workers/platform/limits/#account-plan-limits)).

**Source** ([Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)): "Every RPC method call on a Durable Objects stub is its own RPC session and therefore a single billed request." The Paid cell lists requests as including "HTTP requests, RPC sessions, WebSocket messages, and alarm invocations". The Free plan has 100,000 DO requests per day.

**Source** ([Durable Objects limits FAQ](https://developers.cloudflare.com/durable-objects/platform/limits/#can-i-increase-durable-objects-cpu-limit)): "Durable Objects are Worker scripts, and have the same per invocation CPU limits as any Workers do." The link points to the account plan table, where Free is 10 ms. The FAQ goes on: "By default, the maximum CPU time per Durable Objects invocation (HTTP request, WebSocket message, or Alarm) is set to 30 seconds". The SQLite DO limits table says "CPU per request | 30 seconds (default) / configurable to 5 minutes", with a footnote that each incoming request "resets the remaining available CPU time to 30 seconds". Neither the table nor the footnote separates Free from Paid.

**Inference.**
- A DO RPC from the Worker is a separate invocation with its own CPU accounting. The pricing page counts each stub method call as its own request, the FAQ speaks of "per invocation" limits, and Staging's tail reported the Worker and the DO as two invocations with separate CPU figures.
- Only CPU spent inside the Worker counts against the Worker. The Worker waiting on the DO RPC is I/O.
- An alarm is likewise its own DO invocation.

**Unconfirmed.** Whether the Free plan's per-invocation DO budget is 10 ms or the 30 second default; the DO pages contradict each other. Treat it as 10 ms for planning.

### 1.5 Python Workers differences

**Source.** No Cloudflare page documents a different CPU limit or a CPU optimization guide for Python Workers. The Python pages cover snapshots, packages, FFI and the standard library ([Python Workers](https://developers.cloudflare.com/workers/languages/python/), [How Python Workers work](https://developers.cloudflare.com/workers/languages/python/how-python-workers-work/)). The only CPU remark is that Python versions past their support window may suffer "degraded performance, including higher latency or CPU time usage" ([same page](https://developers.cloudflare.com/workers/languages/python/how-python-workers-work/)).

**Source** (workerd source, per-invocation cost for a `Default` entrypoint). Every invocation constructs a new JavaScript `EntrypointWrapper`, which constructs a new Python instance through `initPyInstance` ([`python-entrypoint-helper.ts` line 522](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/python-entrypoint-helper.ts#L522)). Any method other than `fetch` and `connect`, including `scheduled`, is called through `introspection.wrapper_func` (line 502). It converts every argument with `python_from_rpc` and the return value with `python_to_rpc` ([`introspection.py` lines 79-93](https://github.com/cloudflare/workerd/blob/f136fb7b8da795da989d95a4241d6ded52231f95/src/pyodide/internal/introspection.py#L79)). Cloudflare's RPC docs say the same: "A new instance of the class is created every time the Worker is called" ([Service bindings RPC](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/)).

## 3. Fit for this project

### 3.1 Where the Worker cron path spends 5 to 27 ms

The code path ([`src/worker.py`](../src/worker.py) on `feat/162-detail-parser-cpu`):

- Lines 14-15 import FastAPI and its responses at module level. Lines 17-57 import every app module, including `next_is_you.send_gate` (line 57), which pulls in the scheduler, persistence, the NTUH reader and `html.parser` ([`send_gate.py` lines 12-39](../src/next_is_you/send_gate.py)). Line 1201 builds the whole FastAPI app (`app = create_app()`).
- Lines 1203-1209: `Default` subclasses `asgi.entrypoint(app)`. `scheduled` does `self.env.SEND_GATE.getByName("next-is-you-system")` and `await gate.scheduled_tick()`, nothing else.

**Inference.** The user code in `scheduled` does almost no CPU work, and waiting on the RPC is I/O. Per the snapshot mechanism (1.2), lines 14-57 and 1201 run at deploy time, not per tick. The remaining per-invocation costs:

1. Constructing `Default` and its wrapped `__init__` with `_EnvWrapper` (vendored `python_modules/workers/entrypoints.py` `_wrap_class`).
2. `wrapper_func` converting the controller and the result.
3. Building the DO stub through the env wrapper and converting the RPC result back to Python.
4. In a fresh isolate, the entropy reseed and first-use setup, plus a snapshot restore if that is charged (unconfirmed).

The spread from 5 to 27 ms fits a mix of warm isolates and cold ones, since Cron runs "on underutilized machines". The DO invocation (3 to 8 ms) does far more Python work, yet costs less. That suggests the Worker figure is dominated by per-isolate or per-invocation runtime overhead, not by code. **Unconfirmed** until a comparison is measured (see 3.3).

Whether FastAPI makes this worse is unconfirmed. It can only matter through a larger snapshot. `python_modules/` is 12 MB, including `pydantic_core`.

T3 removes the question. | Unknown, possibly zero | Low | Medium (would mean a second Python Worker) |
| T9 Cron every 2 minutes | Matches the #136 read cadence, but does not lower CPU per invocation | None per invocation | Low: lifecycle deadlines are coarser by a minute | Trivial |

### 3.3 Suggested order and the measurement that settles it

**Inference.**

1. **Settle what the Worker invocation is.** Deploy to Staging a tiny JavaScript Worker with the same `* * * * *` Cron, bound with `script_name` to the existing DO, calling `scheduled_tick()`. Then remove the Cron from the Python Worker. Compare `wrangler tail` `cpuTime` for 15+ ticks, the same method as #162. This is T3 and also the experiment: if the JS invocation is about 1 ms, the 5 to 27 ms was Python Worker overhead.
2. **Bring the DO tick under 10 ms with headroom.** Measure the held DO tick against a Staging copy with realistic `outbound_events` volume. Narrow the ledger digest, then add T6 to the parser. Only then consider T8 splitting and T4 alarms.
3. **Acceptance stays per invocation.** Free gives no average and an unquantified grace. Every invocation, including the reading tick for 3 visits (#22, "One run watches 3 visits at once and records CPU" in [`PRE-LIVE-CHECKLIST.md`](../docs/PRE-LIVE-CHECKLIST.md)), should sit under 10 ms with margin. Ending `ok` while above 10 ms is not evidence of fit.

## Unconfirmed items

- Whether isolate startup or Python snapshot restore is charged to an invocation's `cpuTime`, or counted against its 10 ms.
- The size and shape of the "built-in flexibility": window, count, averaging, or per isolate.
- Whether the Free plan's per-invocation CPU budget for Durable Object RPC and alarms is 10 ms or the 30 second default. The DO limits page and its FAQ disagree.
- Whether a service-binding callee (T5) has its own 10 ms on Free.
- The CPU saving of D1 `batch()` versus separate calls; no source quantifies it.
- How many milliseconds before the limit the Python `CpuLimitExceeded` warning fires.
- Whether local workerd enforces any CPU limit. The #162 local numbers are differences, not a Free-plan check either way.
